# QilyLean OPL 单点培训课件内容标准

> 生效日期：2026-08-27
> 适用范围：自本标准生效日起新生产、新增发布的 OPL（One Point Lesson）单点培训课件。
> 历史课件：暂不追溯修改；后续按专项计划逐步升级。

## 1. 总原则

QilyLean OPL 不以“有页面、有文字、有图表”为完成标准，而以“高营养成分、高技术含金量、可直接用于制造现场培训与工程改善”为交付标准。

每份 OPL 必须做到：

1. **讲清原理**：不仅告诉读者“是什么”，还要解释“为什么、怎么判断、为什么这样做”。
2. **可量化**：涉及节拍、效率、质量、成本、设备、物流、项目管理等主题时，应尽可能给出公式、参数、判定阈值、示例数据或计算逻辑。
3. **可执行**：必须能转化为现场动作、工程步骤、检查表、判断规则或项目推进方法。
4. **有边界**：说明适用条件、不适用条件、常见误区及风险，避免把工具万能化。
5. **有案例**：优先采用制造业现场案例、数据化示例、Before/After 或问题—分析—对策—验证闭环。
6. **有来源意识**：涉及标准、体系或专业方法时，引用标准名称、版本或权威来源；不伪造标准条款与编号。
7. **少口号、多技术**：禁止用大量空泛概念、宣传语、重复定义占据主体篇幅。

## 2. OPL 标准内容骨架

除极简安全/操作类 OPL 外，专业方法类 OPL 建议至少包含以下模块：

1. **主题与学习目标**
   - 这份 OPL 要解决什么问题。
   - 学完后能做什么、判断什么、输出什么。

2. **术语 / 原理 / 机制**
   - 中文定义与英文全称（如适用）。
   - 核心原理、逻辑关系、作用机制。
   - 与相近工具/概念的区别。

3. **关键参数、公式与判定逻辑**
   - 变量定义、单位、数据来源。
   - 公式必须说明口径，避免只有算式没有工程意义。
   - 如存在行业常用阈值，应标明来源或说明“企业内部判定值”。

4. **应用场景与适用边界**
   - 典型适用场景。
   - 不适用或需谨慎使用的场景。
   - 输入条件、前置条件与限制条件。

5. **标准实施步骤 / 工程方法**
   - 按步骤说明执行顺序。
   - 明确责任角色、输入、动作、输出、验证点。
   - 能落到现场表单、系统字段、看板或会议机制更佳。

6. **数据化案例 / 实战示例**
   - 至少给出一个具有工程逻辑的示例。
   - 优先使用“现状 → 分析 → 对策 → 结果”结构。
   - 涉及计算时应展示关键计算过程与结果解释。

7. **常见错误 / 风险 / 失效模式**
   - 列出现场最容易误用、漏用、错判的情形。
   - 对高风险主题明确“不能这样做”的红线。

8. **检查清单 / 自测题 / 现场判断题**
   - 让读者能快速检验是否真正掌握。
   - 问题应围绕实际判断，而非仅复述定义。

9. **输出物 / 管理闭环**
   - 学完后应形成什么：SOP、标准工时、点检表、甘特图、控制计划、改善清单、KPI 等。
   - 必要时说明后续 PDCA / SDCA / 审核 / 复盘机制。

10. **参考依据（适用时）**
    - 标准、规范、体系手册、专业资料、官方文档等。
    - 不强行堆砌引用，但关键技术结论应可追溯。

## 3. 技术含金量质量门槛

新 OPL 发布前按 100 分制自检，**低于 85 分不得作为正式培训课件发布**：

| 维度 | 分值 | 判定要点 |
|---|---:|---|
| 专业深度 | 25 | 原理、机制、专业定义、关键逻辑是否准确且有深度 |
| 工程可操作性 | 20 | 是否能直接转化为步骤、动作、表单、判断规则或管理机制 |
| 数据与量化 | 20 | 是否包含公式、参数、数据示例、阈值、计算或量化验证 |
| 案例与闭环 | 15 | 是否具有问题—分析—对策—验证/标准化闭环 |
| 边界与风险 | 10 | 是否说明适用边界、误区、失效风险及注意事项 |
| 信息结构与可视化 | 5 | 是否便于现场快速理解、培训和复用 |
| 依据与可追溯性 | 5 | 关键标准/专业结论是否有可靠出处或口径说明 |

### 一票否决项

出现以下任一情况，不得发布：

- 只有概念解释，没有应用方法或判断逻辑；
- 大量宣传口号、空泛描述，技术内容明显不足；
- 公式变量或单位不清；
- 编造标准条款、数据、案例或来源；
- 把有明确边界的工具描述为“万能方法”；
- 页面虽精美，但无法支持实际培训或现场执行；
- 最末页缺失 QilyLean 官方信息 / 联系方式。

## 4. 可视化与版式要求

1. 页面优先采用“一页一个核心知识点”的 OPL 思路，避免大段文字墙。
2. 复杂逻辑优先使用：流程图、结构图、因果关系图、时间轴、甘特图、矩阵、公式框、Before/After、红黄绿状态或检查表。
3. 图表必须服务于工程理解，不做纯装饰。
4. 字号、对比度、留白、表格密度应保证电脑、平板及打印/PDF可读。
5. 不因追求简洁而删除关键公式、边界、工程步骤或案例数据。

## 6. 发布前 QA 清单

发布前至少确认：

- [ ] 是否明确解决一个具体问题或知识点；
- [ ] 是否包含原理而不仅是定义；
- [ ] 是否存在可操作步骤；
- [ ] 是否有公式 / 参数 / 阈值 / 数据逻辑（主题适用时）；
- [ ] 是否有至少一个工程案例或现场示例；
- [ ] 是否说明使用边界与常见误区；
- [ ] 是否形成输出物或管理闭环；
- [ ] 是否达到 85/100 技术质量门槛；
- [ ] 是否适配网页阅读与打印/PDF；
- [ ] 最末页是否包含统一官网信息 / 联系方式；
- [ ] 所有标准、数据、来源是否真实可追溯。

## 7. 历史 OPL 处理原则

本标准**不要求立即改动既有 OPL**。历史课件保留现状，后续若启动升级，应优先补足：技术深度、数据化案例、公式/判定规则、适用边界、实战检查清单与统一末页信息。
